# La Tribu

## Objectif
App familiale privée (parents = un compte partagé e-mail + mot de passe ; enfants créés/supprimés dans les réglages, jamais en dur) : tâches récurrentes/ponctuelles confiées aux enfants, points gagnés après validation parent, magasin de récompenses par enfant, ambiance ludique (niveaux, séries, badges, avatar à accessoires achetés en points), style sobre. Smartphone first. Spécifications : `CAHIER_DES_CHARGES.md`. Maquette interactive : `maquette/index.html` (`npx http-server maquette -p 5190`) ; état gardé dans le navigateur (localStorage), « Réinitialiser » dans Réglages, démo chargeable depuis l'état vide.

## Stack (cible)
Node >= 22.5, Express, SQLite (`node:sqlite`), front PWA. Calquée sur `../listes-courses` (Cabas). Monté dans `../node-gateway` sous `/latribu`.

## État
**Étapes 1-5 codées (application complète).** Étape 1 (socle) : installation (premier compte parent), connexion parent (e-mail + mot de passe, scrypt), profils enfants créés/supprimés par les parents (PIN scrypt, verrou 5 min après 5 échecs), **session enfant persistante** (cookie 1 an, révocable). Étape 2 : tâches planifiées (tous les jours / certains jours / chaque semaine / chaque mois / date précise, pour 1 à N enfants, moment matin-après-midi-soir, description, points libres, heure de rappel **stockée mais pas encore notifiée**), missions ouvertes (premier arrivé), génération paresseuse des occurrences, déclaration par l'enfant, validation/refus (avec motif) par le parent, registre de points (solde + XP + niveau, 100 XP/niveau), ajustement libre bonus/pénalité (plancher 0), historique des points enfant et parent. Étape 3 (magasin) : récompenses créées pour 1 à N enfants (description, prix libre, limite par enfant jour/semaine/mois, stock individuel ou partagé), achat avec approbation parent (points et stock réservés à la demande, rendus si refus), objectif d'épargne (étoile), accessoires d'avatar payés avec les mêmes points (prix modifiables par le parent), historique points + récompenses côté enfant et parent. Étape 4 (ludique) : série de jours (toutes les missions faites ; jour sans mission neutre), bonus aux paliers 3/7/14/30 réglables (Réglages), badges automatiques + badges décernés par un parent, célébration niveau/badge au prochain affichage de l'enfant (`kids.level_seen`, `badges.seen`), sons optionnels (localStorage). Étape 5 : PWA (manifeste, icônes `scripts/make-icons.py`, `public/sw.js` réseau d'abord) et notifications Web Push (clés VAPID générées et gardées en base) : rappel de chaque tâche à son heure + second rappel 1 h après, décisions des parents, alertes et résumé quotidien aux parents (réglages). **Non vérifié sur un vrai téléphone** : le navigateur intégré à l'outil de développement refuse les service workers ; à tester sur Android/iPhone (iOS : app installée sur l'écran d'accueil).

Tests : `npm test` (node:test).

**Après audit de sécurité** : verrous de connexion par appareil + profil (cookie `latribu_device`, table `trusted_devices`) et par adresse IP (`LATRIBU_TRUST_PROXY=1` derrière le proxy de l'hébergeur : dernière entrée de `X-Forwarded-For`) ; un tiers ne bloque plus la famille ; au plus 2 calculs scrypt en parallèle (file de 16, sinon 503) ; abonnements push limités aux services des navigateurs (`LATRIBU_PUSH_HOSTS` pour en ajouter) ; textes validés comme chaînes (`util.text`), emoji filtrés (`util.emoji`) et échappés côté interface ; API en `Cache-Control: no-store` ; messages d'erreur internes masqués. Non traités volontairement : installation ouverte tant qu'aucun compte n'existe (créer le compte parent dès le déploiement) et origine partagée de la passerelle (préférer un sous-domaine dédié).
**Fonctions ajoutées** : photo preuve (réglage global désactivé par défaut + option par tâche, JPEG réduit par l'appareil, purge N jours après la décision), changement de PIN (Réglages > Gérer), statistiques hebdomadaires (parent et enfant), bibliothèque de 18 modèles de tâches (modifiable, « Enregistrer comme modèle »), validité des récompenses (dates + activation), file d'attente hors connexion pour le bouton « fait » avec dernière vue de l'enfant gardée (localStorage).
**Sous-tâches** : une tâche peut avoir jusqu'à 12 étapes (`task_steps`, migrations 7-8), cochées par l'enfant sur sa mission (`occurrence_steps`, `PUT /api/occurrences/:id/steps/:step`). Deux modes (`tasks.steps_mode`) : **tout ou rien** (`all`, défaut : points de la tâche, « fait » seulement quand tout est coché) ou **points par sous-tâche** (`each` : chaque étape a ses points, total de la tâche = somme ; l'enfant peut déclarer dès qu'une étape est cochée ; le parent valide étape par étape à l'approbation (`POST /approve` avec `steps` ; la réponse donne `points` = solde et `earned` = points de cette validation), les étapes non faites ou non validées sont perdues ; **bonus facultatif** (`tasks.steps_bonus`, migration 9) ajouté si toutes les étapes sont validées, total possible = somme + bonus ; `occurrences.points` = points réellement gagnés). La date / récurrence reste sur la tâche entière, jamais sur une étape. Modifier une tâche garde les cases cochées des étapes conservées (par `id`). Les modèles de tâches reprennent sous-tâches, mode et bonus (`task_templates.steps` JSON, migration 10) ; deux modèles d'exemple livrés : « Rituel du soir » (3 étapes à 1 point + bonus 2) et « Ranger la cuisine » (tout ou rien).
**Journée parfaite et bravos** (migration 11) : quand toutes les missions *planifiées* du jour d'un enfant sont validées (au moins une), l'écran de célébration s'affiche une fois par jour (`kids.perfect_seen`, calculé par `game.perfectDay`), sans mini-jeu. Bravos : le parent envoie un autocollant (8 fixes dans `game.STICKERS`, mot facultatif de 140 car.) (dessinés en SVG dans `public/app.js`, `STK`/`stk()`, sans fichier image ; `game.STICKERS` garde l'emoji pour la notification) depuis « Bravo » sur la fiche enfant (`POST /api/kids/:id/kudos`, table `kudos`) ; l'enfant reçoit une notification push, une célébration au prochain affichage (`celebrate.kudos`, `kudos.seen`) et la liste « Bravos reçus » sur son accueil (`/api/me`.`kudos`, 14 jours).
**Barème famille et extensions** (migration 12) : série tolérante par enfant (`kids.streak_min`, % de missions planifiées du jour à réaliser, 100 par défaut, réglé dans Enfants > Ajuster ; `PATCH /api/kids/:id` avec `streakMin`) ; tâche ouverte **renouvelable** (`tasks.reopen` = `day` | `week` : après validation, une nouvelle occurrence revient le lendemain ou le lundi suivant, `reopenAfter`) ; **objectif hebdomadaire** sur une tâche planifiée (`goal_count` validations du lundi au dimanche ⇒ bonus `goal_bonus` une fois par semaine, table `goal_awards`) ; **bravo avec points bonus** (`kudos.points`, gagnés = XP). Pack de départ : `lib/seed.js` + `npm run seed-famille -- [--petit Mylo] [--grande Elynn] [--dry-run]` crée tâches, récompenses, prix des accessoires, bonus de série (sans écraser un réglage déjà modifié, relançable) ; le barème (1 point ≈ 3 min, 5 minimum ; rappels matin 7 h, après-midi 16 h 30, soir 18 h) est détaillé dans `docs/BAREME.md` (régénéré par `scripts/make-bareme.js`). Limites des récompenses : par récompense et par enfant, pas par catégorie.
**Voir comme (aperçu parent)** : petit œil en bout de la ligne du nom sur la fiche enfant (Enfants, classe `.eyebtn`). Un parent connecté lit les écrans de l'enfant via l'en-tête `X-View-As: <id>` (`auth.requireKid`, **GET uniquement**, aucune session enfant créée, aucune écriture possible) ; côté interface `S.viewAs`, bandeau « lecture seule » + « Quitter », actions limitées à `VIEW_OK` (navigation), pas de célébration ni de mise en cache hors connexion pendant l'aperçu.
Magasin côté parent (`parentShops`) : une seule liste de récompenses (plus de doublons par enfant), classées par fréquence (jour / semaine / mois / sans limite) puis par prix, avec un filtre par enfant (`S.shopKid`).
Interface parent : les prénoms s'affichent en pastilles à la couleur de l'enfant (`kidBadge`, classe `.kb` ; « Non attribuée » / « Tous » en neutre) sur les tâches, les missions à valider, les demandes d'achat et les récompenses ; les onglets Tâches (enfant, moment) et Magasins (enfant, fréquence) ont un bouton « Filtres » (pastille du nombre de filtres actifs) qui ouvre un panneau (`sheetFilters`, état `S.taskKid`, `S.taskMoment`, `S.shopKid`, `S.shopLimit`) ; les filtres actifs sont rappelés sous le titre avec « Effacer ».
**Boutique d'avatar enrichie** (migration 13) : 31 objets dans `accessories` (`kind` = accessoire / avatar / décor, `slot` = tête / visage / cou / avatar / décor, `art` = clé d'illustration) ; l'enfant porte un objet par emplacement (`kid_equipped`, l'achat équipe aussitôt, `POST /me/accessories/:id/equip` bascule porté / retiré). `publicKid.look` = `{ avatar, scene, head, face, neck }` (clés d'illustration). Les illustrations sont dessinées en SVG dans `public/art.js` (`ART.kidArt`, tête commune pour que tout s'ajuste ; **ajouter un fichier public ⇒ mettre à jour `FILES` et `VERSION` de `public/sw.js`**) ; avatar par défaut = bouille aux couleurs de l'enfant. Côté enfant : onglets Récompenses / Accessoires / Avatars / Décors avec essayage sur son propre look ; prix remis à l'échelle par `seed-famille` (tableau `ACCESSORY_PRICES`).
**Niveaux qui débloquent la boutique** (migration 14) : chaque objet, avatar ou décor a un niveau minimum (`accessories.min_level`, 1 = d'emblée ; réglable dans Magasins > toucher l'objet) ; verrouillé et grisé chez l'enfant (« 🔒 Niveau N »), achat refusé en 409 sinon. La fête de niveau liste les nouveautés franchies depuis `kids.level_seen` (`celebrate.unlocks`) avec un bouton « Voir la boutique ». XP par niveau réglable (`settings.level_xp`, défaut 100, Réglages > Niveaux ; `seed-famille` le passe à 500 car les points sont ×5) : changer l'échelle ramène `level_seen` au nouveau niveau si besoin.
Mission côté enfant (`missionRow`) : icône de la tâche en haut à gauche, grande case « fait » à droite (coche pâle quand elle est vide, grisée tant que les sous-tâches ne le permettent pas, horloge dorée une fois envoyée aux parents, coche verte une fois validée), points dans la ligne du titre ; le titre est barré dès qu'elle est envoyée ou validée (`.task.mission`). **Anti-oubli** : cocher la dernière sous-tâche envoie aussitôt la mission aux parents (`A.step` → `submitMission`, photo demandée avant si exigée) ; en « points par sous-tâche » avec envoi partiel, la case « fait » pulse (`.chk.ready`), une phrase l'indique sous la liste et un encart « Mission commencée » apparaît en haut de l'accueil (`readyBanner`). Les sous-tâches (`stepList`) s'affichent sur toute la largeur sous cette ligne (`.msteps`) avec une grande case à gauche de chacune (`.sbox`), barrée une fois cochée.
**Photo preuve, suite** (migration 15) : le parent décrit la photo souhaitée dans la tâche (`tasks.photo_hint`, champ visible quand « Photo demandée » est activé) ; l'enfant le lit dans le panneau « Photo demandée » avant d'ouvrir l'appareil (`sheetPhotoAsk`). Photo impossible : « Je ne peux pas prendre la photo » + motif, la mission part sans photo (`POST /done` avec `skipPhoto` et `photoNote`, colonnes `occurrences.photo_skipped`, `photo_note`) ; le parent voit « Photo non fournie : motif » à la validation et décide. Une pastille appareil photo marque les tâches qui demandent une preuve (liste parent et missions de l'enfant).
**Envoi tardif et relances** : une mission planifiée non envoyée reste « à faire » le lendemain (réglage `settings.late_send` : `none` / `noon` = jusqu'à midi, défaut / `day` ; `tasks.closeOverdue` passe en « manquée » ensuite), l'enfant la voit dans « Hier · encore à envoyer » (`missions.late`), le parent voit « Pour le JJ/MM » à la validation ; réglable dans Réglages > Envoi tardif. Relances push aux enfants (`notif.nudge`, 19:30 par défaut, Réglages > Notifications) : missions dont des sous-tâches sont cochées mais non envoyées, et le lendemain à 8 h pour celles d'hier tant que l'envoi tardif est ouvert (`push.tick`).
**Design v4 (clair, moderne, pour ados)** : maquette de référence dans l'artefact « La Tribu · maquette design v4 ». Thème clair uniquement (plus de mode sombre automatique), accent = **couleur de l'enfant** (8 couleurs `PAL`, `kids.palette`, choisie par le parent à la création ou dans Réglages > Gérer, ou par l'enfant dans Moi > Ma couleur via `PUT /api/me/palette` ; `--acc` est surchargé côté enfant, `--violetl`/`--violetd` en dérivent par `color-mix`), violet de la marque côté parent, polices **Space Grotesk** (titres, chiffres, boutons) et **Inter** hébergées dans `public/fonts/` (licence OFL ; la CSP n'autorise pas Google Fonts), pièce dorée devant les points (`.pts::before`), navigation flottante (`#nav`/`.tabs`), carte joueur violette avec avatar dans un anneau de progression du niveau et prochain déblocage (`/api/me`.`nextUnlock`), case « fait » ronde, célébration de niveau en anneau. Tout est dans la fin de `public/style.css` (bloc « Design v4 »).

## Fichiers clés
- `server.js` — app Express exportée (statique, `/api`, page avec `<base>` = `{{ROOT}}`).
- `lib/db.js` — SQLite `data/latribu.db` (`LATRIBU_DATA_DIR`), migrations par `PRAGMA user_version` : ne jamais modifier une migration déployée, en ajouter une.
- `lib/tasks.js` — tâches, génération des occurrences (`generate()` idempotente, invalidée à chaque modif), cycle déclaré/validé/refusé. `lib/points.js` — registre `movements` (solde = SUM(delta), XP = SUM(xp)). `lib/dates.js` — dates AAAA-MM-JJ, fuseau Europe/Brussels, lundi = 1.
- `lib/game.js` — séries, bonus, badges, célébrations. `lib/push.js` — abonnements, envois, `tick()` (rappels + résumé, fenêtre de 10 min, anti-doublon `notif_log`), minuteur 1 min `unref` (`LATRIBU_PUSH=off` le coupe ; `LATRIBU_VAPID_SUBJECT` = contact transmis au service de push). `lib/settings.js` — réglages clé/valeur.
- `lib/photos.js` (photo preuve), `lib/stats.js` (semaine lundi-dimanche), `lib/templates.js` (modèles de tâches).
- `lib/shop.js` — récompenses, achats (transactions : le solde et le stock ne peuvent pas être dépassés), objectif, accessoires.
- `lib/auth.js` — sessions en base (rôle parent/enfant), empreintes, limiteurs. `lib/api.js` — routes. `lib/util.js`, `lib/security.js`.
- `public/` — `index.html`, `style.css`, `app.js` (SPA sans build, CSP sans script en ligne). `maquette/` — référence visuelle et fonctionnelle (état local, non reliée à l'API).
- `scripts/set-password.js` — secours : `npm run set-password -- <email> <mot de passe>`.

## Contraintes node-gateway
- `module.exports = app` ; `listen()` et handlers globaux uniquement sous `if (require.main === module)`.
- Chemins front/API relatifs, cookies `path=/latribu`. Pas de `process.exit()`. Exception assumée : un seul `setInterval` (1 min, `unref`, jamais d'exception) dans `lib/push.js` pour les rappels, lancé à l'import.
- Lancement local : jonction `node-gateway/apps/latribu` -> ce dépôt (déjà créée), puis `npm start` dans la passerelle (`/latribu/`). Seul : `PORT=5191 npm start`.

## Modèle de données non évident
- Session enfant persistante après le PIN (cookie longue durée), révocable par un parent.
- Tâche planifiée pour N enfants = N occurrences liées par `tid` ; répétitions : tous les jours / certains jours / chaque semaine / chaque mois / date précise. Récompense créée pour N enfants = N entrées de catalogue ; stock par enfant par défaut, ou stock partagé (compteur commun) ; limite par enfant par jour/semaine/mois ; stock réservé à la demande, rendu si refus.
- Descriptions facultatives sur tâches et récompenses ; historique points + récompenses côté enfant et parent.
- Points libres (gain, prix, ajustement) ; aucun lien avec l'euro. Accessoires payés avec le même solde.
- Tâche : moment (matin/après-midi/soir) + heure de rappel push.
- Solde = somme du registre `mouvements` (jamais d'UPDATE) ; XP séparé, ne diminue jamais.
- Achat : points ET stock réservés à la demande (movement négatif `Réservé : …`), rendus si refus (movement `Remboursé : …`, sans XP). Limite par enfant comptée sur `purchases.created_date` (hors refusés). Stock partagé = `rewards.stock` + `shared=1` ; individuel = `reward_kids.stock`. Modifier le stock d'une récompense le réinitialise.
- Tâche = deux axes indépendants : **quand** (`kind` plan = récurrence/date/moment/rappel, ou open = sans date ni moment, jamais manquée, à faire une fois) et **pour qui** (`task_kids` ; aucun enfant = non attribuée : une occurrence libre `kid_id` NULL, le premier enfant qui la prend la verrouille ; plan non attribuée = une occurrence libre par échéance). Les tâches ouvertes ne comptent pas dans les séries.
- Interface : icônes via `iconField()` (favoris + catalogue par catégorie + emoji collé) ; les actions de formulaire (`LOCAL` dans app.js) mettent la fiche à jour sur place, sans recharger ni rejouer l'animation.
- Occurrence = tâche x enfant x date (mission ouverte : `kid_id` NULL jusqu'à la prise, `due_date` = jour de la prise) ; statuts : à faire / en attente / validée / refusée / manquée.

## Mises à jour et déploiement
- **Tout l'état durable est dans la base SQLite** (`data/latribu.db`, ou `LATRIBU_DATA_DIR`) : comptes, enfants, points, **réglages de notification** (table `settings`), **clés VAPID**, **abonnements push par appareil**. Une mise à jour du code ne doit donc jamais écraser ce dossier : en production (copie dans `apps/latribu`), garder `data/` à part (ou définir `LATRIBU_DATA_DIR` hors du dossier déployé) et ne copier que le code.
- **Déploiement via GitHub** (détails : `docs/DEPLOIEMENT.md`) : sur le serveur, `curl -fsSL https://raw.githubusercontent.com/Gatomlo/LaTribu/main/scripts/install.sh | bash` depuis le dossier de la passerelle (clone ou `git pull --ff-only` dans `apps/latribu`, `npm install --omit=dev`, essai de chargement, `data/` jamais touché, refuse si fichiers modifiés à la main ; `REF=<commit>` pour revenir en arrière), puis redémarrer le site. Première installation : créer le compte parent par `npm run set-password` AVANT d'ouvrir le site. Déploiement automatique facultatif : `.github/workflows/ci.yml` (tests + audit à chaque push ; job SSH inactif tant que la variable de dépôt `DEPLOY_ENABLED` n'est pas `true`, secrets dans l'environnement `production`). Adresse du client : `X-Forwarded-For` (dernière entrée) n'est lue que si la connexion vient d'une adresse locale/privée ou si `LATRIBU_TRUST_PROXY=1`.
- **Connexion centralisée de node-gateway** (`lib/gateway-bridge.js` = copie de référence de la passerelle, `lib/auth.js`) : crochet `app.gatewayAccounts` (comptes parents en lecture seule, lu au démarrage), `req.gateway` → droit `admin` + rattachement (compte local > e-mail > identifiant) à un compte parent existant = session locale de 2 h non prolongée ; `latribu_nogw` suspend la reconnexion automatique après « Se déconnecter » (`POST /api/gateway/login` la rétablit) ; création du premier compte fermée aux anonymes derrière la passerelle. Vérifié de bout en bout avec la vraie passerelle (`/_gw/admin/apps/latribu/accounts`). Mode d'emploi : `docs/DEPLOIEMENT.md` §3 bis.
- Migrations : uniquement additives (`lib/db.js`), jouées au démarrage ; avant toute migration d'une base existante, une **sauvegarde datée** est faite dans `data/backups/` (5 conservées). Les réglages lus sont fusionnés avec des valeurs par défaut (`{...DEFAULTS, ...stocké}`) : un nouveau réglage ne réinitialise jamais les anciens.
- Clé VAPID : ne jamais la régénérer (tous les abonnements deviendraient invalides). Si la base est restaurée ou la clé change, l'app se réabonne seule à l'ouverture (`pushSync`) et le service worker gère `pushsubscriptionchange`.
- Service worker : changer `VERSION` et `FILES` dans `public/sw.js` quand un fichier est ajouté ; les abonnements push survivent aux changements de version.
- Icônes : `python scripts/make-icons.py` (Pillow) régénère l'icône de l'app (« la tribu » : trois bouilles souriantes sur dégradé violet-rose-orange, aussi dessinée en SVG), le favicon, l'icône monochrome `badge-96.png` et une icône par type de notification (`notif-reminder|ok|reward|review|alert.png`, choisies dans `lib/push.js` via `ICONS`). `tests/update.test.js` vérifie que tout ce qui est référencé existe.
